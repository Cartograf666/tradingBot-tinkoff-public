# Настройка GitHub

Публичный репозиторий выполняет исследовательскую программу, а отдельный приватный репозиторий хранит результаты. Оба должны принадлежать одному владельцу. Для этого проекта хранилище — `Cartograf666/tradingBot-tinkoff`; его видимость должна оставаться приватной.

## Доступы и переменные

В публичном репозитории откройте **Settings → Secrets and variables → Actions**.

| Вид | Имя | Значение / назначение |
| --- | --- | --- |
| Variable | `MARKET_STUDY_DATA_REPOSITORY` | `Cartograf666/tradingBot-tinkoff` — отдельное приватное хранилище |
| Variable | `MARKET_STUDY_ENABLED` | `false` до успешного `preflight`; затем `true` для расписания с обязательной пробой |
| Secret | `TINKOFF_API_TOKEN_SANDBOX` | Отдельный токен песочницы Т-Банка |
| Secret | `MARKET_STUDY_STORAGE_TOKEN` | Отдельный fine-grained GitHub token для приватного хранилища |

Для storage token выберите только один приватный репозиторий, разрешение **Contents: Read and write** и обязательное **Metadata: Read**. Он нужен для записи журнала, создания draft Release и загрузки архивов. Установите срок действия, покрывающий исследование. Не используйте вместо него общий токен входа GitHub CLI. [Создание fine-grained token](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens).

Обычный `GITHUB_TOKEN` публичного workflow имеет только чтение содержимого и статусов Actions своего репозитория и не заменяет storage token. Рабочий токен брокерского счёта `TINKOFF_API_TOKEN` для этого workflow не требуется и не используется вместо sandbox secret.

Для TLS-подключения к официальной песочнице workflow использует [проверенный публичный сертификат](../certs/README.md) из SDK Т-Банка. Системное хранилище доверия не меняется, проверка имени сервера и сертификатов сохраняется.

Secrets не добавляют в исходники, workflow, issues или сообщения. Перенос локального токена в GitHub — отдельное действие владельца. [Использование Actions Secrets](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets).

## Первый запуск

1. Выполните **Actions → Market study (public compute, private data) → Run workflow → check** на `main`. Это проверка кода без ключей.
2. Настройте два Secrets и две Variables выше; оставьте `MARKET_STUDY_ENABLED=false`.
3. В любое время суток выполните `preflight` на `main`. Программа проверит sandbox-токен через метаданные акций и календарь, запись журнала в приватную ветку и загрузку небольшого диагностического архива. Результат содержит ближайшее торговое окно. Этот режим не проверяет поток рынка и не засчитывается в исследование.
4. Проверьте успешное завершение workflow и наличие `preflight-*.tar.gz` в приватном draft Release. При ошибке оставьте расписание выключенным.
5. После успеха измените `MARKET_STUDY_ENABLED` на `true`. Подготовки запланированы на 03:17/03:47/04:17 МСК для утра и 08:17/08:47/09:17 для дня; дополнительные события — на 08:20/08:35 и 13:20/13:35. Без секретов задачи ждут 08:50/13:50. GitHub может доставить событие позже указанного времени. Программа дождётся начала соответствующего окна из календаря и автоматически запишет 60 секунд, проверит качество, выполнит воспроизведение и подтвердит загрузку `smoke-*.tar.gz`. Только затем начнётся основная запись. Ошибка любой стадии прервёт этот блок; следующая плановая попытка снова выполнит проверку. Одновременного разрешения на обход пробы переменная не даёт.

Кроме ранних подготовок, для защиты от одиночного пропуска GitHub предусмотрены шесть резервных возможностей запуска: **08:50, 08:55, 09:00, 09:05, 09:10, 09:15** и **13:50, 13:55, 14:00, 14:05, 14:10, 14:15** МСК по будням. Все задачи, обращающиеся к брокеру (`campaign`, `preflight`, `smoke`, `observe`), используют одну очередь; работающая запись не отменяется. Подготовка и отчёты могут идти параллельно. GitHub может заменить лишнюю ожидающую задачу более новой. Поздний запуск собирает оставшееся окно, если до его конца есть не менее двух минут; утренний запуск после 14:00 переходит в дневной блок. В приватной квитанции фиксируется режим RECOVERY и первоначальные границы сессии. Уже подтверждённые и завершившиеся интервалы пропускаются. Запоздалое начало не сдвигает границы дня и не улучшает показатели качества. После закрытия окна — `SKIPPED` без новой попытки записи.

Смотрите итог задачи: `CAPTURED` означает завершившуюся попытку записи блока или его остатка, `SKIPPED` — отсутствие нового сбора с указанной причиной. Зелёный служебный запуск сам по себе не означает собранный день. Наличие расписания и ручной `smoke` не доказывают автоматическое срабатывание: для этого нужен запуск с **event=schedule**. [GitHub допускает задержки и пропуски событий расписания](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule); эти повторы снижают риск, но не являются независимым от GitHub планировщиком.

Две пробы в день не включаются в расчёт доходности. Их время и подготовка остаются пропусками при подсчёте полноты всей сессии. Пороги 99% общего покрытия и 80% пригодных секунд каждой акции сохраняются; день с большими пропусками не засчитывается. Независимую пробу можно повторить вручную режимом `smoke` во время основной сессии.

Для ручного `campaign` также требуется включение; поздний запуск может собрать остаток текущей основной сессии. При выключенном `MARKET_STUDY_ENABLED` календарное расписание не собирает рынок.

Для ближайшего блока можно заранее запустить **mode: arm**, выбрав `early` или `late`. Уже созданная задача GitHub без секретов ждёт сегодняшних 08:50/13:50 МСК, затем отдельная задача выполняет обычный `campaign`. Ожидание ограничено менее чем 348 минутами; прошедшее время и перенос на следующий день запрещены. Резерв и события расписания используют общую очередь одного блока: резерв не создаёт параллельный сбор. Ручной `arm` — однократная подготовка ближайшего блока. События расписания используют тот же этап ожидания автоматически каждый будний день. Если событие задержалось, ожидание пропускается, а обычная проверка окна решает, разрешён ли сбор; поздний запуск собирает остаток сессии, а закрытая сессия получает `SKIPPED`. Статус `prepare` означает ожидание, а не получение рыночных данных; отмена или ошибка подготовки не разрешает сбор.

Все действия с секретами разрешены workflow только для основной ветки публичного репозитория. Перед чтением и записью хранилище проверяется через GitHub API; совпадение с публичным репозиторием, другой владелец, отсутствие ключей или публичная видимость хранилища останавливают запуск.

## Управление циклом

| Mode | Что происходит |
| --- | --- |
| `check` | Сборка и тесты, ключи не нужны |
| `preflight` | В любое время: sandbox-метаданные/календарь, запись журнала и пробного приватного архива; нужны оба ключа, рыночный поток не проверяется |
| `smoke` | Короткая sandbox-запись, диагностика и приватный архив |
| `observe` | Запись сейчас до сегодняшних 13:50 МСК либо более раннего окончания основной сессии, частями до 30 минут; диагностическая, без зачёта полного дня |
| `campaign` | Автоматическая проба, затем один из двух блоков основной сессии; требует включения и допустимого времени |
| `arm` | Заранее создаёт задачу ближайшего сегодняшнего блока, ждёт времени подготовки без секретов, затем выполняет `campaign` |
| `report` | Обновляет приватные отчёты о полноте и активности; storage token для данных и автоматически выдаваемый GitHub token для статусов |
| `status` | Фаза и счётчики из приватного журнала; нужен только storage token |
| `freeze` | После 10 пригодных дней фиксирует реализацию и переводит исследование к 10 новым HOLDOUT-дням; нужен только storage token |

В фазе `READY_TO_FREEZE` сбор приостанавливается для оценки результатов. `freeze` — явное действие владельца, а не автоматический подбор прибыльной стратегии. HOLDOUT проверяется на той же зафиксированной реализации. После 10 пригодных HOLDOUT-дней фаза становится `COMPLETE`.

Ручной `observe` предназначен для пропущенного начала утра. Он требует открытой основной сессии, сначала выполняет минутный smoke, затем сохраняет части и их независимые симуляции в приватные `diagnostic-*.tar.gz`. Абсолютная граница останавливает поток даже с учётом времени подготовки метаданных. Эти части не попадают в журнал, DEVELOPMENT/HOLDOUT и дневную статистику; капитал в каждой диагностической симуляции начинается заново. Ошибка воспроизведения сохраняет исходную часть перед остановкой. `observe` использует общую очередь рыночных команд. Подготовка `arm late` может ждать параллельно, но запись дневного блока начнётся только после освобождения общей очереди.

Если завершённая минутная проба не проходит качество, её исходные данные и причины отказа тоже сохраняются в приватном `smoke-*.tar.gz` перед остановкой. Такой архив сам по себе не подтверждает успешный старт: в `study-smoke.json` требуется `quality.status=PASS` и выполненный replay.

В `campaign`, `observe` и ручном `smoke` теперь до трёх минутных проб с паузой 15 секунд. Повторяется только отказ **качества завершённой записи**, причём лишь после подтверждения её приватного архива. Ошибки записи/доступа, проверки целостности, симуляции или хранилища завершают запуск сразу. Суммарный бюджет проверки — не более восьми минут; перед новой пробой должно оставаться хотя бы 90 секунд. При своевременном campaign проверка ограничена исходным 20-минутным окном старта; при RECOVERY получает свежий бюджет до восьми минут с запасом 20 секунд до конца блока. В observe действует граница 13:50. Пробы не сдвигают часы частей или знаменатель полноты дня; потраченное время остаётся реальным пропуском. Пороги 99%/80%, протокол и условия зачёта дней сохранены.

Сводка каждого запуска Actions показывает попытки, причины вроде «VKCO: пригодно 47 из 60 секунд, требуется минимум 48», ожидание повтора и результат. Исчерпание попыток остаётся красным отказом с понятной аннотацией «Сбор не начат», а не скрывается под успешным статусом. Успешная стартовая проверка отдельно предупреждает, что длительный сбор ещё не завершён. Публичная сводка содержит только разрешённые названия инструментов и счётчики качества; котировки, сделки, результаты стратегии и ключи туда не попадают.

В длинном диагностическом архиве исходная запись и её replay лежат в отдельных соседних папках; путь к отчёту указан в `diagnostic-observation.json`. Успешная минутная проба подтверждает только старт: завершение каждой длинной части, её обработки и приватной загрузки проверяется отдельно. При отказе обработки архив сохраняется с `replayFailed=true` и `failureStage`, а задача завершается ошибкой.

Для остановки будущих запусков установите `MARKET_STUDY_ENABLED=false`. Уже выполняющийся workflow нужно отдельно отменить в Actions. Сохраняются только подтверждённые загрузки; отмена может сделать день неполным.

## Где смотреть результаты

- Приватный репозиторий → ветка `observation-state`: `study-ledger.json` и сводка `README.md`.
- Приватный репозиторий → Releases → draft `market-study-archive-v1`: исходные части и дневные отчёты.
- Публичный репозиторий → Actions: состояние выполнения, тесты и служебные счётчики, без публикации рыночных архивов.

Работа идёт на стандартном публичном Ubuntu runner. Каждый блок ограничен 350 минутами, вся кампания — 60 попытками. GitHub не гарантирует точное время запуска: неполные дни отмечаются как недостаточные данные. Менять приватный репозиторий с архивами на публичный не следует — проверка предотвращает новые загрузки, но не может скрыть уже опубликованные владельцем файлы.

## Восстановление и контроль полноты

Метаданные sandbox запрашиваются с ограниченными повторами: до четырёх попыток,
10 секунд на попытку, паузы 1/2/5 секунд. Повторяются только распознанные таймауты
и временные gRPC-ошибки; отказ авторизации, неподдерживаемые метаданные и отмена
не повторяются. Общий срок части ограничивает запросы, ожидание и поток. В campaign
передаётся точное окончание части с прежним запасом 5 секунд; подготовка расходует
это окно. Последний кусок основной сессии проверяется по фактически оставшемуся времени.

После исчерпания временных запросов неудачная запись сначала сохраняется отдельным
приватным `failure-*.tar.gz`. В пределах того же окна возможна одна дополнительная
попытка всей записи; затем программа переходит к следующему исходному интервалу.
Неизвестные ошибки, ошибки доступа, обработки и хранилища останавливают блок.
Пропуски остаются пропусками. Неудачные архивы не становятся canonical-частями.

В приватной ветке `observation-state/operations/` хранится ход каждой попытки,
в `reports/daily-YYYY-MM-DD.json` — полнота и причины незачёта. Это операционная
диагностика, она не меняет научный протокол и не добавляет успешные дни.
`mode=report` работает без брокерского ключа: восстанавливает подтверждённые receipts,
пытается завершить полный прошлый день по сохранённому плану и фиксирует неполные дни.
Повторный отчёт не заменяет immutable canonical-части. Отдельный workflow
`Market study daily completeness` запускается после завершения/падения сборщика
ежечасно в 09:37–19:37 МСК и дополнительно в 19:25. Время доставки событий GitHub не гарантирует. Резкое уничтожение runner может оставить
текущую локальную часть несохранённой; подтверждённые приватные архивы сохраняются.

Поле `collector` сверяет статусы и активные шаги GitHub: подготовка/очередь, запуск, запись, диагностика, остановка либо неизвестное состояние. Следующий архив ожидается к исходной границе части плюс три минуты на сохранение; превышение отмечается как `UPLOAD_OVERDUE`. Без доступа к статусам отчёт сохраняет `UNKNOWN`, а служебная задача завершается ошибкой. Старая запись CAPTURING сама по себе не доказывает активность. `unarchivedClosedWindows` показывает уже закрывшиеся интервалы без подтверждённых архивов; это не оценка свежести данных внутри сохранённых частей. Пока календарь дня неизвестен, счётчик равен null. Smoke/observe не входят в счётчики исследования.

Диагностика свежести в `summary.json` разделяет возраст события при получении,
интервалы обновления конкретного стакана, общий поток и регулярность таймера.
Порог 2000 мс и качество 99%/80% не изменены. Старые записи можно проверить
`node .study-dist/src/report/diagnose-freshness.js /absolute/recording-directory`:
CLI читает их без изменения, явно указывает текущую версию анализатора и не
подменяет исходное происхождение отчёта. Редкое обновление инструмента и общая
задержка доставки — разные наблюдения; эти измерения не доказывают, на каком
участке между провайдером и обработчиком возникла общая задержка.

## Запуск только средствами GitHub

Расписание Actions, раннее ожидание `arm`, повторы запуска и автоматические
отчёты работают без внешнего сервиса и без агента. Дополнительные аккаунты или
ключи планировщика не требуются. Cloudflare не используется; подготовленный
ранее модуль удалён по решению владельца от 16.09.2026.

Раннее создание задачи оставляет запас на задержку события, но не гарантирует
точное время старта. Если GitHub пропустит все события или задержит runner за
пределы допустимого окна, день останется неполным; пороги качества не меняются.
Для проверки после публикации используйте `mode=smoke`: sandbox-запись,
проверка качества, воспроизведение и подтверждённая приватная загрузка. После
окончания workflow автоматически обновится отчёт о полноте дней. Проба не
засчитывается как полный день и не подтверждает доходность.

Приёмка эксплуатации: fault-injection проверки, реальный час с переходом между
частями, затем две полные автоматические сессии с исходными порогами качества.
До завершения этих наблюдений стабильность всей сессии не считается доказанной.

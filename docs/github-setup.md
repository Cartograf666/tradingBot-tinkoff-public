# Настройка и работа на GitHub

Публичный `Cartograf666/tradingBot-tinkoff-public` выполняет программу, приватный `Cartograf666/tradingBot-tinkoff` хранит данные. Основной сценарий читает sandbox API: торговых заявок, создания счетов и пополнений нет. Компьютер владельца, агент и внешний планировщик не нужны.

## Доступы

В публичном репозитории используются **Settings → Secrets and variables → Actions**:

| Вид | Имя | Назначение |
| --- | --- | --- |
| Variable | `MARKET_STUDY_DATA_REPOSITORY` | `Cartograf666/tradingBot-tinkoff` |
| Variable | `MARKET_STUDY_ENABLED` | `true` включает плановый сбор; `false` запрещает новые campaign |
| Secret | `TINKOFF_API_TOKEN_SANDBOX` | Токен песочницы Т-Банка |
| Secret | `MARKET_STUDY_STORAGE_TOKEN` | GitHub token с доступом к приватному хранилищу |

Версия непрерывного сбора использует эти же доступы. Новые ключи, аккаунты, внешние сервисы и платные runners не нужны.

При первоначальной настройке storage token ограничивают одним приватным репозиторием, **Contents: Read and write**, **Metadata: Read**, со сроком действия на период исследования. [Документация fine-grained token](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens). Обычный `GITHUB_TOKEN` workflow читает только публичный репозиторий и его статусы Actions; заменить им доступ к приватному хранилищу нельзя. Рабочий брокерский `TINKOFF_API_TOKEN` этот workflow не использует.

Secrets не переносят в исходники, issues или сообщения. Код с секретами выполняется только из основной ветки. Перед записью программа проверяет владельца, имя и приватность хранилища. TLS использует [проверенный публичный сертификат](../certs/README.md); проверка сертификатов и имени сервера сохраняется.

## Первый запуск и проверка обновления

1. На `main` запустите **Actions → Market study (public compute, private data) → Run workflow → check**: сборка и тесты без ключей.
2. Для первоначальной установки задайте перечисленные доступы и оставьте `MARKET_STUDY_ENABLED=false`.
3. Режим `preflight` в любое время проверяет sandbox-метаданные, календарь, запись журнала и маленького приватного архива. Рыночный поток этим ещё не проверен.
4. Режим `continuous-pilot` выполняет 180 секунд записи с сегментами каждые 30 секунд. Он скачивает их из приватного GitHub, сверяет SHA-256, восстанавливает исходные события и манифест, запускает replay. Доказательство сохраняется как `continuous-pilot-proof-*.tar.gz`. У теста отдельная очередь и предел 10 минут на весь job; одновременно идёт только один такой тест. Он не отменяет основной сбор и не попадает в научный журнал.
5. После проверки включите `MARKET_STUDY_ENABLED=true`. Для существующей установки значение и доступы сохраняются при обновлении.

## Непрерывная запись

`campaign`/`arm` подтверждают приватное сохранение и ждут окна из календаря API. Один поток обслуживает весь торговый блок; проверки подписок, heartbeat и переподключение работают внутри этого потока. Отдельная стартовая проба качества в `continuous-v2` отменена. Низкая пригодность одной акции не запрещает запись остальных; ошибки доступа, исчерпание восстановления подписок или хранения останавливают сбор явно.

Каждые пять минут закрытый файл подтверждается в приватном draft Release. Контрольная точка содержит исходные байты, границы последовательности, хеш предыдущей точки и неизменяемые метаданные. Смена файла не создаёт переподключений, новых ACK или подставленных стаканов. Загрузка последовательная; максимум два неподтверждённых сегмента, до 120 секунд на операцию. При жёстком падении надёжной границей является последняя подтверждённая загрузка, а не обещание потери строго пяти минут.

После окончания сохраняется полный сырой блок. Научные получасовые окна становятся маленькими архивами-ссылками на него. Дневной replay читает каждый исходный поток ровно один раз: границы файлов и окон не сбрасывают стратегию, позиции или капитал. Реальный разрыв соединения остаётся разрывом. Старые архивы продолжают читаться; несовместимые версии записи нельзя смешать в принятый день.

Пороги сохранены: **99% секунд всей основной сессии**, **80% пригодных секунд каждой из шести акций**, возраст стакана **не более 2000 мс**. Подготовка, поздний старт и пропуски входят в полный знаменатель. Прибыль не участвует в выборе пригодных данных. Технический успех и `INSUFFICIENT_DATA` могут существовать одновременно.

## Расписание

Основная сессия берётся из актуального API-календаря; граница двух блоков — 14:00 МСК. Ранние подготовки: **03:17/03:47/04:17 МСК** для утра и **08:17/08:47/09:17** для дня. Дополнительные — **08:20/08:35** и **13:20/13:35**. Без секретов задачи ждут 08:50/13:50. Резервные события идут каждые пять минут с 08:50 до 09:15 и с 13:50 до 14:15 по будням.

Основной сбор и прежние `preflight`/`smoke`/`observe` используют общую очередь без отмены работающего job. Подготовки, отчёты и ограниченный `continuous-pilot` независимы. Опоздавший утренний запуск после 14:00 выбирает дневной блок. Сохраняются исходные границы и режим `RECOVERY`; до закрытия должно оставаться не менее двух минут. Завершившееся окно получает `SKIPPED`, уже подтверждённый полный блок не записывается повторно.

[GitHub допускает задержку и пропуск schedule](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule). Наличие расписания или успешный ручной тест не доказывают точного автоматического старта. Ранние подготовки и резерв уменьшают риск; полного устранения этой зависимости внутри GitHub нет.

## Управление

| Mode | Результат |
| --- | --- |
| `check` | Сборка и тесты без ключей |
| `preflight` | Проверка sandbox-метаданных и приватной записи, без рыночного потока |
| `continuous-pilot` | Трёхминутная проверка непрерывной записи, удалённого восстановления и replay |
| `smoke` | Прежняя минутная проба с проверкой качества; до трёх ограниченных повторов |
| `observe` | Прежний диагностический утренний сбор до 13:50, частями до 30 минут, с предварительным smoke |
| `campaign` | Непрерывная запись доступного блока основной сессии; требует включения |
| `arm` | Ожидание ближайшего сегодняшнего блока без секретов, затем campaign |
| `report` | Восстановление receipts, обработка загруженных блоков и честная сводка полноты; без ключа брокера |
| `status` | Текущее состояние научного журнала |
| `freeze` | Явная фиксация проверенной версии после 10 пригодных DEVELOPMENT-дней; затем 10 новых HOLDOUT-дней |

Один job ограничен 350 минутами, исследование — 60 попытками. Автоматического выбора выигрышной стратегии нет. `CAPTURED` означает завершение попытки записи, а не принятый полный день. Для остановки будущих campaign задают `MARKET_STUDY_ENABLED=false`; выполняющуюся задачу отдельно отменяют в Actions. Подтверждённые приватные архивы сохраняются.

## Результаты и восстановление

- Приватная ветка `observation-state`: `study-ledger.json`, `operations/`, `reports/daily-YYYY-MM-DD.json` и сводка `README.md`.
- Приватный draft Release `market-study-archive-v1`: checkpoints, полные исходные блоки, ссылки научных окон и отчёты.
- Публичные Actions: тесты, статусы и разрешённые служебные счётчики. Рыночные архивы в публичные Actions artifacts не загружаются.

Неопределённый ответ после upload сверяется с удалённым размером и хешем: совпадающий asset переиспользуется, конфликт не перезаписывается. Сбой между загрузкой окна и записью журнала восстанавливается по receipt внутри архива. Полный сырой блок, сохранённый до сбоя обработки, повторно обрабатывается отчётом при совпадении версии анализатора. Ошибка одного такого источника не отменяет формирование остальных операционных сводок; источник остаётся незасчитанным, report сообщает ошибку.

Checkpoint-prefix без финального манифеста восстанавливается как неполная запись, без выдуманного `stop` или COMPLETE. Его не засчитывают как научный день. При восстановлении проверяются порядок сегментов, последовательность событий, хеши и исходные метаданные.

`Market study daily completeness` срабатывает после завершения основного workflow, ежечасно в 09:37–19:37 МСК и дополнительно в 19:25. Поле `collector` сверяет текущие статусы и активные шаги GitHub; сохранённое CAPTURING не доказывает активность. Проверяются срок следующей контрольной точки и последняя подтверждённая загрузка. Научные окна оцениваются после блока: отсутствие их отчёта во время записи не означает отсутствия checkpoints. Недоступность проверки обозначается UNKNOWN.

`summary.json` показывает возраст событий, интервалы обновления стаканов и регулярность таймера. Старую запись можно исследовать без изменения: `node .study-dist/src/report/diagnose-freshness.js /absolute/recording-directory`. Анализатор указывает свою версию и не подменяет происхождение исходных данных.

Cloudflare и другие внешние планировщики не используются. Проверка длинной непрерывной работы и двух полных автоматических сессий остаётся отдельным наблюдением; короткий pilot и программные тесты не подтверждают доходность или надёжность всей будущей сессии.

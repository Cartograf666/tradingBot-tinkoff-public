# Настройка GitHub

Публичный репозиторий выполняет исследовательскую программу, а отдельный приватный репозиторий хранит результаты. Оба должны принадлежать одному владельцу. Для этого проекта хранилище — `Cartograf666/tradingBot-tinkoff`; его видимость должна оставаться приватной.

## Доступы и переменные

В публичном репозитории откройте **Settings → Secrets and variables → Actions**.

| Вид | Имя | Значение / назначение |
| --- | --- | --- |
| Variable | `MARKET_STUDY_DATA_REPOSITORY` | `Cartograf666/tradingBot-tinkoff` — отдельное приватное хранилище |
| Variable | `MARKET_STUDY_ENABLED` | `false` до успешного `preflight`; затем `true` для расписания с обязательной пробой |
| Secret | `TINKOFF_API_TOKEN_SANDBOX` | Отдельный токен песочницы Т-Банка |
| Secret | `MARKET_STUDY_STORAGE_TOKEN` | Отдельный fine-grained GitHub token для приватного хранилища |

Для storage token выберите только один приватный репозиторий, разрешение **Contents: Read and write** и обязательное **Metadata: Read**. Он нужен для записи журнала, создания draft Release и загрузки архивов. Установите срок действия, покрывающий исследование. Не используйте вместо него общий токен входа GitHub CLI. [Создание fine-grained token](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens).

Обычный `GITHUB_TOKEN` публичного workflow имеет только чтение содержимого своего репозитория и не заменяет storage token. Рабочий токен брокерского счёта `TINKOFF_API_TOKEN` для этого workflow не требуется и не используется вместо sandbox secret.

Secrets не добавляют в исходники, workflow, issues или сообщения. Перенос локального токена в GitHub — отдельное действие владельца. [Использование Actions Secrets](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets).

## Первый запуск

1. Выполните **Actions → Market study (public compute, private data) → Run workflow → check** на `main`. Это проверка кода без ключей.
2. Настройте два Secrets и две Variables выше; оставьте `MARKET_STUDY_ENABLED=false`.
3. В любое время суток выполните `preflight` на `main`. Программа проверит sandbox-токен через метаданные акций и календарь, запись журнала в приватную ветку и загрузку небольшого диагностического архива. Результат содержит ближайшее торговое окно. Этот режим не проверяет поток рынка и не засчитывается в исследование.
4. Проверьте успешное завершение workflow и наличие `preflight-*.tar.gz` в приватном draft Release. При ошибке оставьте расписание выключенным.
5. После успеха измените `MARKET_STUDY_ENABLED` на `true`. По будням GitHub подготовит блоки в 08:50 и 13:50 МСК. Программа дождётся начала соответствующего окна из календаря и автоматически запишет 60 секунд, проверит качество, выполнит воспроизведение и подтвердит загрузку `smoke-*.tar.gz`. Только затем начнётся основная запись. Ошибка любой стадии прервёт этот блок; следующая плановая попытка снова выполнит проверку. Одновременного разрешения на обход пробы переменная не даёт.

Две пробы в день не включаются в расчёт доходности. Их время и подготовка остаются пропусками при подсчёте полноты всей сессии. Пороги 99% общего покрытия и 80% пригодных секунд каждой акции сохраняются; день с большими пропусками не засчитывается. Независимую пробу можно повторить вручную режимом `smoke` во время основной сессии.

Для ручного `campaign` также требуется включение; запуск принимается только в допустимое время соответствующего блока. При выключенном `MARKET_STUDY_ENABLED` календарное расписание не собирает рынок.

Все действия с секретами разрешены workflow только для основной ветки публичного репозитория. Перед чтением и записью хранилище проверяется через GitHub API; совпадение с публичным репозиторием, другой владелец, отсутствие ключей или публичная видимость хранилища останавливают запуск.

## Управление циклом

| Mode | Что происходит |
| --- | --- |
| `check` | Сборка и тесты, ключи не нужны |
| `preflight` | В любое время: sandbox-метаданные/календарь, запись журнала и пробного приватного архива; нужны оба ключа, рыночный поток не проверяется |
| `smoke` | Короткая sandbox-запись, диагностика и приватный архив |
| `campaign` | Автоматическая проба, затем один из двух блоков основной сессии; требует включения и допустимого времени |
| `status` | Фаза и счётчики из приватного журнала; нужен только storage token |
| `freeze` | После 10 пригодных дней фиксирует реализацию и переводит исследование к 10 новым HOLDOUT-дням; нужен только storage token |

В фазе `READY_TO_FREEZE` сбор приостанавливается для оценки результатов. `freeze` — явное действие владельца, а не автоматический подбор прибыльной стратегии. HOLDOUT проверяется на той же зафиксированной реализации. После 10 пригодных HOLDOUT-дней фаза становится `COMPLETE`.

Для остановки будущих запусков установите `MARKET_STUDY_ENABLED=false`. Уже выполняющийся workflow нужно отдельно отменить в Actions. Сохраняются только подтверждённые загрузки; отмена может сделать день неполным.

## Где смотреть результаты

- Приватный репозиторий → ветка `observation-state`: `study-ledger.json` и сводка `README.md`.
- Приватный репозиторий → Releases → draft `market-study-archive-v1`: исходные части и дневные отчёты.
- Публичный репозиторий → Actions: состояние выполнения, тесты и служебные счётчики, без публикации рыночных архивов.

Работа идёт на стандартном публичном Ubuntu runner. Каждый блок ограничен 350 минутами, вся кампания — 60 попытками. GitHub не гарантирует точное время запуска: неполные дни отмечаются как недостаточные данные. Менять приватный репозиторий с архивами на публичный не следует — проверка предотвращает новые загрузки, но не может скрыть уже опубликованные владельцем файлы.
